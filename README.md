# RawChords — аккорды и разборы песен

Минималистичный сайт: публичный каталог разборов плюс своя библиотека песен —
текст с аккордами над слогами, аппликатуры, транспонирование, капо, заметки к
местам трека.

Имя бренда задано один раз — `SITE_NAME` в [lib/site.ts](lib/site.ts). Оттуда его
берут заголовок вкладки, `og:site_name`, `applicationName`, структурированные
данные главной и вордмарк на картинке превью. Страницы свой бренд в `title` не
дописывают: хвост подставляет шаблон в корневом layout.

*Ключи в localStorage (`tabs.draft.v1.*`, `tabs.viewer.v1.*`) намеренно оставлены
со старым префиксом — переименование стёрло бы у всех черновики и настройки
читалки.*

**Стек (целевой):** Next.js (App Router) + TypeScript · PostgreSQL + Prisma ·
Auth.js · Tailwind · деплой Vercel + Neon.

## Как запустить

**Требования:** Node 18+ (проверено на 24), npm. Внешняя БД **не нужна** —
локально используется SQLite (файл `prisma/dev.db`).

```bash
npm install            # + postinstall сгенерирует Prisma-клиент
npm run db:push        # создать таблицы в SQLite (файл prisma/dev.db)
npm run dev            # http://localhost:3000
```

Файлы окружения уже созданы (оба в `.gitignore`):
`.env` → `DATABASE_URL="file:./dev.db"`, `.env.local` → сгенерированный
`AUTH_SECRET`. Если их нет — создайте: `DATABASE_URL` как выше, а секрет —
`npx auth secret`.

**Первые шаги:** `/register` → создать аккаунт → `/songs` → «+ Новая» → редактор
с живым превью → «Сохранить». Публичные разборы со всех аккаунтов — на `/browse`
(«Все песни» в шапке).

**Сброс базы:** удалите `prisma/dev.db` и снова `npm run db:push`.

**Полезные команды:**

| Команда | Что делает |
| --- | --- |
| `npm run dev` | Dev-сервер (hot-reload) |
| `npm run build` / `npm start` | Прод-сборка / запуск |
| `npm test` | Юнит-тесты (парсер, транспонирование, капо, валидация) |
| `npm run typecheck` | Проверка типов |
| `npm run db:push` | Синхронизировать схему с БД |
| `npm run db:studio` | Prisma Studio — просмотр БД в браузере |

### Продакшн-БД: не потерять данные при наборе пользователей

Локальный SQLite (`prisma/dev.db`) — **только для разработки**: это файл на
машине, на Vercel (serverless, read-only FS) он не работает. Для реальных
пользователей нужна постоянная БД — **Neon (Postgres)**, где данные durable и
резервируются. Схема уже переносима (без enum'ов и провайдер-специфики), поэтому
переезд — несколько шагов, **без потери текущих данных**:

1. `npm run db:export` — выгрузит все данные в `data-export.json` (пользователи,
   песни, аккаунты, лайки, избранное, аннотации, сетлисты).
2. Создать проект в [Neon](https://neon.tech), взять **pooled** строку.
3. В `prisma/schema.prisma`: `provider = "sqlite"` → `"postgresql"`.
4. `DATABASE_URL` (в `.env`) → строка Neon; на Vercel задать `DATABASE_URL`,
   `AUTH_SECRET`, `AUTH_GOOGLE_ID/SECRET` в Environment Variables.
5. `npm run db:push` — создаст таблицы в Neon.
6. `npm run db:import` — зальёт `data-export.json` в Neon (в правильном порядке,
   с сохранением id и дат).

После этого можно набирать пользователей — данные в Neon не теряются. `data-export.json`
в `.gitignore` (содержит хеши паролей). `postinstall` генерирует Prisma-клиент на сборке.

## Фаза 1 — что уже есть

Чистые модули без зависимостей от UI, 45 юнит-тестов.

```
lib/
  chords/
    pitch.ts      ноты ↔ pitch class (0..11), выбор диез/бемоль
    chord.ts      разбор/сборка/транспонирование аккорда
    key.ts        тональности, выбор написания, капо
  chordpro/
    types.ts      AST песни
    parse.ts      парсер ChordPro → AST
    transform.ts  транспонирование целой песни
```

### Ключевые решения

- **Написание нот зависит от целевой тональности.** При транспонировании
  сначала вычисляется целевая тональность (`transposeKey`), из неё берётся
  предпочтение диез/бемоль (`accidentalForKey`), и уже им форматируются все
  аккорды. Пример из ТЗ: `A` + 1 полутон → `Bb`-мажор → нота пишется `Bb`, а не
  `A#`. Таблицы имён тональностей и `accidentalForKey` согласованы по кругу
  квинт (относительный минор берёт то же написание: Gb-мажор ↔ Ebm).
  - *Известный компромисс:* написание выбирается по тональности, а не по
    гармонической функции конкретного аккорда — как в большинстве
    транспонировщиков. Теоретические тональности (Cb, E# внутри Gb/F#) не
    выделяются отдельно. Для гитарного песенника этого достаточно.

- **Разбор аккордов.** Корень `[A-G][#b]*`, затем суффикс (переносится как есть:
  `maj7`, `m7b5`, `sus4`, `add9`, `7#9`), опциональный бас после `/`.
  Транспонируются только корень и бас. Не-аккорды (`N.C.`, `%`, произвольный
  текст) проходят без изменений.

- **Капо — отдельно от транспонирования.** Реальное звучание не меняется; капо
  влияет только на показываемые аппликатуры. Итоговый сдвиг форм =
  `транспонирование − лад капо` (`capoShapeShift`). Реальная тональность
  показывается отдельно.

- **Якоря аннотаций.** Парсер хранит номер исходной строки (1-based) на каждой
  строке AST — на них будут навешиваться заметки в фазе 5.

- **Секции.** `{start_of_chorus|verse|bridge|tab}` (+ короткие `soc/sov/sob/sot`)
  и парные `end_*`. Метка секции берётся из значения директивы. Текст вне секций
  попадает в секцию `none`.

## Фаза 2 — рендер

Next.js (App Router) + Tailwind v4. Тёмная тема по умолчанию, одна акцентная
краска, крупная типографика, mobile-first.

```
app/
  layout.tsx        корневой layout, тёмная тема, viewport
  globals.css       тема (@theme) + CSS раскладки аккордов
  page.tsx          лендинг
  demo/page.tsx     демо рендера: ± транспонирование, показать/скрыть аккорды
components/
  ChordSheet.tsx    рендер песни (чистый компонент)
lib/chordpro/
  columns.ts        раскладка строки в колонки (чистая логика, покрыта тестами)
```

### Как устроен рендер

- **Аккорд строго над слогом.** Каждая колонка (`.cs-col`) — inline-block с двумя
  строками: аккорд сверху (`.cs-chord`, фиксированная высота), слог снизу
  (`.cs-lyric`). Никакого выравнивания пробелами в моноширинном шрифте.
- **Перенос между колонками.** `lineToColumns` режет строку на слова; пробел
  между словами становится точкой переноса (реальный текстовый узел-пробел между
  inline-block). Аккорд в середине слова (`дру[C]зья`) склеивает соседние колонки
  без пробела — слово не рвётся, аккорд остаётся над своим слогом.
- **Показать/скрыть аккорды** — класс `chordsheet--nochords` (строка читается как
  обычный текст).
- Транспонирование применяется вызывающим кодом (`transposeSong`) до рендера;
  компонент чистый. Написание нот следует за целевой тональностью (проверено
  живьём: G +3 → Bb-мажор, аккорды бемолями).

## Дизайн-система

Направление — «тёплый песенник под лампой»: тёмная тёплая база, один акцент
(ламповый янтарь `#e6a23c`), много воздуха, крупная типографика. Тёмная тема по
умолчанию, mobile-first, без сайдбаров/хлебных крошек.

- **Шрифты** (`next/font/google`, оба с кириллицей): **Spectral** — антиква для
  заголовков/вордмарка (`--font-display`); **Golos Text** — гротеск под кириллицу
  для интерфейса и текстов песен (`--font-sans`).
- **Токены** — в `app/globals.css` через `@theme` (`--color-bg/surface/fg/muted/
  line/accent`, `--w-app: 48rem`). Утилиты Tailwind (`bg-bg`, `text-accent`,
  `border-line`…) генерируются из них.
- **Компонентные классы** — в `@layer components` (чтобы утилиты Tailwind их
  перебивали): `.container-app` (ширина контента, 48rem — чуть шире на десктопе),
  `.site-header`, `.btn` + `.btn-primary/outline/ghost`, `.icon-btn`, `.field`,
  `.card`, `.eyebrow`, `.display`, `.toolbar`, `.key-readout`, `.cs-*`.
- **Атмосфера** — мягкое ламповое свечение сверху + едва заметное зерно
  (`body::before/after`, позади контента, не влияют на читаемость).
- **Шапка** (`components/SiteHeader.tsx`) — тонкая, липкая, знает о сессии.
- **Проверено** на desktop и 375px: без горизонтального переполнения, панель
  песни в одну строку, транспонирование в панели работает (G +3 → Bb).

## Фаза 3 — БД + аккаунты

Prisma (PostgreSQL/Neon) + Auth.js v5 (email + пароль).

```
prisma/schema.prisma   модели: User, Account, Session, VerificationToken,
                       Song, Annotation, Setlist, SetlistItem
lib/db.ts              синглтон Prisma
lib/auth.ts            конфиг Auth.js (Credentials, JWT-сессии, Prisma-адаптер)
lib/password.ts        bcrypt hash/verify (тесты)
lib/validation.ts      email/пароль (тесты)
types/next-auth.d.ts   расширение типов сессии (user.id)
app/api/auth/[...nextauth]/route.ts
app/(auth)/actions.ts  серверные экшены: login, register
app/(auth)/login, register  формы
app/page.tsx           главная знает о сессии (вход/выход)
```

### Решения

- **Email + пароль** через Credentials-провайдер. Стратегия сессии — **JWT**
  (Credentials несовместим с сессиями в БД). Пароли — bcrypt (12 раундов),
  поле `User.passwordHash` поверх стандартной схемы Auth.js.
- **Adapter Prisma** подключён на будущее (magic-link / линковка аккаунтов) —
  модели `Account`, `Session`, `VerificationToken` уже в схеме.
- **`Song.visibility`** — enum, по умолчанию **`private`** (как в ТЗ).
- **`Annotation.anchor`** — строка (номер строки из парсера либо id секции);
  `type` — enum `technique|rhythm|transition|note`.
- **`SetlistItem`** — упорядоченная связь m2m (`order`, уникальность пары
  сетлист+песня).
- Защита маршрутов — через `await auth()` в серверных компонентах (не middleware,
  чтобы не тащить bcrypt/Prisma в edge-runtime).

### База данных

Локально — **SQLite** (`prisma/dev.db`), поднимается одной командой
`npm run db:push`, внешних сервисов не требует. Схема переносима на
**PostgreSQL / Neon** для production — см. «Как запустить» → «Деплой».

Проверено вживую: регистрация создаёт пользователя, авто-вход по JWT, создание/
просмотр песен и заметки пишутся и читаются из БД.

- **Каталог** `/browse` — публичный (без входа): все песни с visibility `public`

  не попадают; страница `noindex`. Ссылка «Все песни» в шапке видна всем.
- **Страница песни** `/songs/[id]` — `SongViewer`: ± транспонирование (крупная
  целевая тональность), **слайдер капо** (показывает аппликатуры относительно

  с регулируемой скоростью, **wake lock** (экран не гаснет), **печать/PDF** без
  разрыва куплетов (`break-inside: avoid`). Видимость проверяется на сервере;
  `private` — только владельцу; все страницы песен `noindex`.
- **Редактор** `/songs/new`, `/songs/[id]/edit` — слева textarea ChordPro, справа
  живое превью; поля title/artist/key/capo/tempo/visibility (по умолчанию
  **private**); удаление с подтверждением.
- Проверено вживую (`/demo`): капо 2 при тональности G → реальная остаётся **G**,
  формы уезжают в **F** (`F C Dm Bb F`); панель в одну строку на 375px без
  переполнения.

## Фаза 5 — аннотации

```
lib/annotations.ts                     list/create/delete (гейт по владельцу песни)
app/(site)/songs/annotations-actions.ts  серверные экшены
components/AnnotationForm.tsx           форма добавления (useActionState + автосброс)
components/ChordSheet.tsx               + опциональная интерактивность строк
components/SongViewer.tsx               + заметки под строками
```

- **Клик по строке → заметка.** Каждая лирическая строка кликабельна (для
  владельца); клик разворачивает форму под строкой. Тип: техника / ритм / переход
  / заметка. Заметки показываются под своими строками с бейджем типа.
- **Якорь = номер исходной строки** из парсера (`LyricLine.line`) — стабильная
  привязка, не зависящая от транспонирования/капо.
- **Приватность.** Заметки — личные: страница отдаёт их только владельцу
  (`canAnnotate`); создание/удаление проверяют владение песней на сервере.
- Заметки печатаются вместе с песней (форма и подсказки — скрыты на печати).
- Проверено вживую (`/demo`): заметки рендерятся под нужными строками с русскими
  бейджами; клик по строке разворачивает форму с полями (тип, текст, якорь).

## Быстрый ввод аккордов (палитра)

Чтобы не печатать вручную `[Am]` по 4–5 раз на строку (скобки + переключение
раскладки кириллица↔латиница), в редакторе над текстом — **палитра аккордов**
([ChordPalette.tsx](components/ChordPalette.tsx)):

- **Аккорды тональности** — диатонические трезвучия текущего `key`
  (`diatonicChords` в [key.ts](lib/chords/key.ts), напр. Am → Am Bdim C Dm Em F G).
  Обновляются при смене тональности.
- **В песне** — аккорды, уже встречающиеся в тексте (повторы и свои — в один клик).
- **Своё поле** — произвольный аккорд (напр. `F#m7`), после вставки становится
  чипом в ряду «В песне».

Клик по чипу вставляет `[Аккорд]` в позицию курсора, возвращает фокус в поле и
двигает курсор за скобку — можно сразу продолжать. Печатать скобки и переключать
раскладку для аккордов больше не нужно.

## Библиотека аппликатур (диаграммы аккордов)

- **Панель аккордов над текстом** — все аккорды песни (в порядке появления, с
  учётом транспонирования) показаны **сразу крупными диаграммами**
  ([ChordCard](components/ChordCard.tsx), [ChordDiagram](components/ChordDiagram.tsx)).
- **Аккорды в самом тексте** — при наведении/тапе всплывает аппликатура
  ([InlineChord](components/InlineChord.tsx)).
- **Аппликатуры стандартных аккордов — автоматически:** встроенные open-формы +
  генератор барре-форм E-типа для major/m/7/m7/maj7 ([diagrams.ts](lib/chords/diagrams.ts),
  покрыт тестами). Поэтому обычные разборы не требуют ручной работы.
- **Квинты (power chords)** в нотации «лад + В/Н» генерируются автоматически:
  `NВ` — верхняя (струны 6/5/4, лады `N, N+2, N+2`), `NН` — нижняя (струны 5/4/3).
  Напр. `8В` → 6-я 8, 5-я 10, 4-я 10. Ничего задавать вручную не нужно.
- **Прочие кастомные аккорды** (нестандартные обозначения) — задаются
  интерактивным грифом ([FretboardEditor](components/FretboardEditor.tsx)): выбор
  начального лада + клик по струнам (○/× сверху). Хранятся на песне
  (`Song.chordDefs`, JSON) и имеют приоритет над встроенными.

## Личный кабинет (`/account`)

- **Профиль** — аватар, имя, email, «аккаунт с …», выход. Редактируется
  ([ProfileEditor.tsx](components/ProfileEditor.tsx)): **загрузка аватара**
  ([AvatarInput.tsx](components/AvatarInput.tsx) — файл сжимается на клиенте в
  data URL, как обложки; общий ресайз в [resizeImage.ts](lib/resizeImage.ts)) и
  имя. Аватар из Google подхватывается автоматически.
- **Публичный профиль автора** `/u/[id]` (доступен всем, `noindex`) — аватар, имя
  и все **публичные** разборы автора. Открывается кликом по нику автора в каталоге
  (клик по строке ведёт на песню, ник — на профиль, паттерн «растянутой ссылки»).
- **Дата создания разбора** показывается на странице песни («добавлено …»).
- **Вкладки** — «Избранное» и «Лайкнутое» (то, что откладывали): списки песен со
  счётчиками. Данные — `listFavoriteSongs` / `listLikedSongs` / `getLibraryCounts`
  в [engagement.ts](lib/engagement.ts); чужие приватные песни не показываются.
- **Строка списка** вынесена в общий [SongRow.tsx](components/SongRow.tsx)
  (обложка, название, мета, лайки, чипы аккордов); [Avatar.tsx](components/Avatar.tsx)
  общий для шапки и кабинета.
- **Вход в кабинет** — из шапки (аватар + имя → `/account`); «Выйти» переехал в
  кабинет.
- *Известное:* имя/аватар в шапке берутся из JWT-сессии и обновляются при
  следующем входе; страница кабинета читает БД напрямую и всегда актуальна.

## Каталог, вовлечённость и вход

- **Главная = каталог** (`/`) — публичные разборы со всех аккаунтов, поиск только
  по названию/исполнителю (фильтр тональности убран). Старый `/browse` удалён.
- **Лайки и избранное** — модели `Like` / `Favorite` (уникальны на пару
  пользователь+песня), тоггл-действия ([engagement.ts](lib/engagement.ts),
  [engagement-actions.ts](app/(site)/songs/engagement-actions.ts)). Кнопки на
  странице песни; **счётчик лайков в каталоге** (иконка + число, минималистично).
  Просмотр «моих лайков/избранного» — позже, в личном кабинете.
- **Просмотры считаются и у гостей.** Раньше учитывались только вошедшие —
  аккаунт был защитой от накрутки. Но каталог публичный и индексируемый, почти
  весь трафик приходит из поиска без входа, и сортировка «Популярные»
  ранжировала по узкой прослойке залогиненных. Гость опознаётся **не кукой**, а
  суточным отпечатком «соль + дата + IP + User-Agent»
  ([visitor.ts](lib/visitor.ts)): куку видно из JS и её чистка обнуляет счёт,
  отпечаток так просто не сбросить; куки нет вовсе — не нужен баннер согласия;
  сырой адрес никуда не пишется, в БД уходит только необратимый хеш.
  - **Боты отсеиваются по User-Agent** (покрыто тестами). Без этого краулеры,
    обходящие каждый разбор, превратили бы счётчик в меру частоты обхода;
    превьюшники ссылок в мессенджерах — тоже не читатели.
  - Цена — недосчёт: за одним внешним адресом (NAT, оператор, офис) несколько
    человек с одинаковым браузером сольются в одного. Для ранжирования терпимо:
    недосчёт бьёт по всем разборам одинаково и не меняет порядок, а накрутка
    порядок ломает.
  - В `View` заполнено ровно одно из `userId` / `visitorId`. Два уникальных
    индекса вместо одного работают потому, что Postgres считает NULL
    различными значениями, и каждый сторожит только «свой» вид записей.
  - Соль — `VIEW_SALT` (по умолчанию `AUTH_SECRET`), см. `.env.example`.
- **Шапка** — «Поиск» (иконка) вместо «Все песни», «Мои песни» с иконкой,
  «Войти» — яркой акцентной кнопкой (`btn-primary`).
- **Google-вход** — кнопка «Продолжить с Google» на входе/регистрации показывается
  всегда. Провайдер работает, когда заданы `AUTH_GOOGLE_ID` / `AUTH_GOOGLE_SECRET`;
  без них клик даёт понятное сообщение (`/login?google=unconfigured`), а не ошибку
  Google. Линковка по email включена (Google подтверждает адреса). Настройка — в
  `.env.example`.
- **Обложка на странице песни** заполняет высоту шапки (до кнопок лайка) —
  обёртка-div со `align-self: stretch`, картинка `object-fit: cover`.
- **Видимость при создании** — карточки с иконками (🌐/🔗/🔒), по умолчанию —
  **публичная** ([VisibilitySelect.tsx](components/VisibilitySelect.tsx)).
- **Палитра аккордов больше не сбрасывает скролл** поля: чипы не забирают фокус
  (`onMouseDown` preventDefault), позиция скролла восстанавливается при вставке.

## Чтение и список: размер шрифта, чипы аккордов, заметка автора

- **Размер шрифта текста** — на странице песни в настройках (шестерёнка) кнопки
  `A−`/`A+` (диапазон 0.8–1.7rem, сброс). Размер задаётся CSS-переменной
  `--sheet-font-size` на обёртке листа. Дефолт немного уменьшен (1.05rem).
- **Чипы аккордов в списках** — справа у каждой песни (`/songs` и `/browse`)
  маленькие квадратики с аккордами в порядке первого появления, без повторов
  (`chordsInOrder` в [usedChords.ts](lib/chordpro/usedChords.ts), покрыт тестами).
  Напр. «17 ножевых» → `2Н 3В 5Н 5В`. Тональность/видимость ушли в подстроку.
- **Заметка от автора** — поле `Song.note`, показывается блоком **над текстом**
  на странице песни (видна всем, печатается). Редактируется в редакторе.

## Оформление песен: серый текст и обложки

- **Серые заметки.** Текст аннотаций — приглушённо-серый (`--color-muted`), бейдж
  типа — ещё бледнее, чтобы не спорить с текстом песни.
- **Инлайн-серый текст в песне:** участок между знаками `%` рендерится серым, а
  сами `%` убираются. Пример: `[Em]пой %(× 2)%`. Работает вместе с аккордами
  (`[C]%проигрыш%`), состояние сбрасывается на каждой строке. Реализовано в
  чистом `lib/chordpro/columns.ts` (поле `Column.muted`), покрыто тестами.
- **Обложки треков.** Поле `Song.coverUrl`. В редакторе — загрузка файла, который
  сжимается на клиенте (canvas, ≤512px, JPEG) в data URL и хранится прямо в БД,
  без внешнего хранилища. Показ: крупно на странице песни (рядом с заголовком) и
  миниатюрой слева в списках `/songs` и `/browse` (без обложки — заглушка с
  нотой). В экшене принимаются только `data:image/*` URL.

## Два инструмента: гитара и укулеле

Разбор принадлежит одному инструменту (`Song.instrument` — `"guitar"` либо
`"ukulele"`, по умолчанию гитара). Текст ChordPro инструмент-независим, поэтому
меняется только то, что рисует гриф, и то, в каком каталоге песня показана.

- **Реестр инструментов** — [instruments.ts](lib/chords/instruments.ts): число
  струн, строй (высоты открытых струн), подписи струн, таблица открытых форм,
  семейство подвижных (барре) форм и флаг поддержки квинт «лад + В/Н» (это
  гитарная запись из русских табов, на укулеле её нет).
  - Гитара: 6 струн, EADGBe, подвижные формы E-типа с корнем на 6-й струне.
  - Укулеле: 4 струны, GCEA, подвижные формы **A-типа** с корнем на 1-й струне —
    `[n+2,n+1,n,n]` мажор, `[n+2,n,n,n]` минор, `[n,n+1,n,n]` 7,
    `[n,n,n,n]` m7, `[n+1,n+1,n,n]` maj7.
- **Таблица аппликатур укулеле проверена, а не выписана по памяти.**
  [instruments.test.ts](lib/chords/instruments.test.ts) — независимый «оракул»:
  интервалы качеств заданы в самом тесте, каждая форма разбирается обратно в
  звучащие ноты (`soundingPcs`) и сверяется с названием — лишних нот нет, корень
  и терция на месте, септима у септаккордов тоже. Покрыты все открытые формы и
  12 корней × 5 качеств × оба инструмента. **Новые формы добавлять только с
  зелёным этим тестом.**
- **Каталог разделён:** `/` — гитара (адрес не менялся, все ссылки и позиции в
  поиске сохранились), `/ukulele` — укулеле. Обе страницы — один
  [CatalogView](components/CatalogView.tsx), различаются инструментом и мета.
  Переключатель — обычные ссылки (индексируется, можно поделиться), поисковый
  запрос переносится между каталогами. `/ukulele` добавлен в sitemap.
- **Своя библиотека тоже разделена** — не фильтр на общем списке, а два
  каталога: `/songs` (гитара) и `/songs/ukulele`, общий
  [LibraryView](components/LibraryView.tsx). У каждого свой счётчик во вкладках
  и своя кнопка «Новая», которая открывает редактор с уже выбранным
  инструментом (`/songs/new?instrument=…`).
  - `songs/ukulele` — статический сегмент, поэтому Next разрешает его раньше
    динамического `songs/[id]`; id разборов — cuid, так что песни по такому
    адресу быть не может. Проверено: `/songs/ukulele` → 307 на вход,
    `/songs/<cuid>` → 200, несуществующий id → 404.
- **Диаграммы** ([ChordDiagram](components/ChordDiagram.tsx)) берут число струн
  из самой формы. `size` — это размер *шестиструнной* диаграммы, а остальные
  масштабируются пропорционально (`diagramWidth`/`diagramHeight`), поэтому шаг
  между струнами одинаковый: гитарный viewBox остался ровно `0 0 62 74`,
  у укулеле — `44.4`.
- **Редактор грифа** ([FretboardEditor](components/FretboardEditor.tsx)) получает
  число колонок через CSS-переменную `--fb-strings`, а порожек рисуется по классу
  `.fb-cell--top` (диапазон `nth-child` зависел бы от числа струн).
- **Смена инструмента у песни** отбрасывает несовпадающие аппликатуры:
  `parseChordDefs(json, instrument)` проверяет длину формы, и шестиструнная форма
  не попадёт на четырёхструнный гриф — вместо кривой диаграммы честно
  предлагается задать форму заново.
- **Бейдж инструмента** в строках списков показывается только когда это НЕ
  гитара: гитара — основной случай, подпись в каждой строке была бы шумом.
- **Иконки инструментов** ([InstrumentIcon](components/InstrumentIcon.tsx)) —
  простые контуры: головка грифа, гриф, корпус, розетка. Готовой иконки укулеле
  нет ни в Lucide, ни в Tabler, ни в Feather, поэтому нарисованы свои.
  Различаются **пропорциями, а не деталями**: гитара занимает бокс целиком
  (высота 20 из 24, корпус 9.2, выраженная талия), укулеле заметно короче и
  меньше (16 и 7). На 17 пикселях в шапке работает именно разница силуэтов —
  любая мелкая деталь там сливается.
- **Публичный профиль автора** (`/u/[id]`) — вкладки по инструментам (появляются
  только если у автора есть разборы больше чем для одного) и поиск по его
  разборам. Здесь это параметры запроса, а не отдельные адреса: спроса на
  «автор X укулеле» в поиске нет, а плодить тонкие индексируемые страницы ради
  фильтра незачем — `canonical` всегда указывает на базовый `/u/[id]`.
  Счётчики во вкладках считаются без учёта поиска, иначе вкладки исчезали бы по
  мере ввода.
- **Метаданные** песни и страницы исполнителя собираются по факту: «аккорды на
  гитаре» / «на укулеле» / «на гитаре и укулеле» (у исполнителя может не быть ни
  одного гитарного разбора). Мотив грифа в og-картинке тоже рисуется по числу
  струн.
- **`/demo?instrument=ukulele`** — тот же демо-разбор на любом инструменте.
  Единственный способ увидеть аппликатуры, не заходя в аккаунт (страницы
  редактора закрыты авторизацией).

## Черновики, нижняя навигация, постраничный каталог

- **Черновик редактора в localStorage** ([draft.ts](lib/draft.ts), покрыт
  тестами). Правки уходят в хранилище через 0.7 с после последнего ввода, плюс
  принудительно при сворачивании вкладки (`visibilitychange`/`pagehide`) — иначе
  последние секунды набора пропадали бы. При следующем открытии редактор
  **предлагает** восстановить (баннер «Восстановить / Удалить»), а не подменяет
  текст молча. Ключ свой у каждой песни (`tabs.draft.v1.<id>`, у новой — `new`).
  - Обложка в черновик не попадает: data URL весит десятки килобайт и упирается
    в квоту, а восстанавливается повторной загрузкой файла.
  - Отпечаток содержимого (`draftSignature`) не включает аппликатуры: редактор
    аппликатур пересобирает свой JSON под текущий набор аккордов, и он может
    отличаться от записанного в БД, хотя пользователь ничего не менял.
  - Черновик стирается в момент отправки формы и пишется заново, если сервер
    вернул ошибку (значит, сохранения не было).

- **Нижняя навигация на телефоне** ([MobileNav.tsx](components/MobileNav.tsx)):
  каталог · мои · **+ новая** (акцентная кнопка по центру) · кабинет. До неё
  дотягивается большой палец, тогда как шапка требует перехвата телефона.
  Активный пункт подсвечен пятном и риской сверху; при прокрутке вниз панель
  уезжает за край и возвращается при движении вверх — во время чтения песни
  экран остаётся целиком под текстом. От `sm` панель скрыта, там работает
  обычная шапка (её навигация на телефоне, наоборот, спрятана — не дублируем).

- **Каталог постранично** — `listPublicSongs` отдаёт `{ songs, hasMore }`
  порциями по `CATALOG_PAGE_SIZE`; первая страница приходит с сервера в HTML (и
  индексируется), следующие — кнопкой «Показать ещё»
  ([LoadMoreCatalog.tsx](components/LoadMoreCatalog.tsx) + серверный экшен).
  `hasMore` считается без `COUNT`: берём на одну строку больше запрошенного.
  В сортировку добавлен `id` — иначе строки с равным ключом разъезжаются между
  страницами и дублируются при подгрузке.

- **Поиск считается в БД**, а не в JS. Раньше выборка сначала обрезалась
  потолком в 60 строк, и фильтр применялся уже к ней: песня за пределами этой
  страницы **не находилась вовсе**. Теперь условие уходит в `where` до `take`,
  поэтому ищется вся база.

## Поиск: по словам песни и с опечатками

- **Ищем по тексту, а не только по названию.** Люди помнят строчку, а не
  заголовок. Искать прямо по `body` нельзя: там аккорды в скобках и директивы в
  фигурных, из-за чего фраза, разорванная аккордом (`дру[C]зья`), не находится,
  а по запросу «am» находится половина каталога. Поэтому при сохранении песни
  собирается денормализованная колонка `Song.searchText` — название, исполнитель
  и слова без разметки, в нижнем регистре
  ([searchText.ts](lib/chordpro/searchText.ts), покрыт тестами).
  - Существующие строки заполняются один раз: `node scripts/backfill-search.mjs`.
  - Логика очистки продублирована в скрипте: скрипты в проекте — `.mjs` без
    сборки, TypeScript-модуль напрямую не импортируется. При изменении правил
    править оба места.
- **Опечатки.** Если точных совпадений нет, каталог показывает похожие и честно
  подписывает: «По запросу „…“ ничего не нашлось. Показаны похожие». Основано на
  `pg_trgm`: `node scripts/setup-search.mjs` ставит расширение и GIN-индекс по
  `searchText` (он же ускоряет обычный поиск подстроки).
  - Берётся **`word_similarity`**, а не `similarity`: последняя нормируется на
    длину всей строки, и короткий запрос против текста песни целиком даёт ~0.04.
    Замеры на живой базе: «влеченте» → «влечение» 0.667, «вличение» 0.500,
    «маршрудка» → «маршрутка» 0.600, «детскаятравма» → «детская травма» 0.857.
    Отсюда порог **0.45**.
  - Подбор запускается только для первой страницы и запросов от 3 символов:
    у односимвольного запроса близость к любому слову с этой буквой равна 1.0,
    и «похожим» оказывался весь каталог.
  - Транслитерация не ловится (триграммы «капсайз» и «cupsize» не пересекаются) —
    это ограничение подхода, а не баг.
  - Своя библиотека и профиль автора ищут только точным совпадением: подбор
    похожих сделан для каталога, где происходит поиск незнакомого.

## Модерация: подтверждённые разборы

- **Роль в БД**, а не в токене: `User.role` (`"user" | "admin"`). JWT-сессия
  живёт долго, и права, положенные в токен, применились бы только со следующим
  входом. Проверка — `isAdminUser` в [admin.ts](lib/admin.ts), обёрнута в
  `cache()`, поэтому на страницу приходится один запрос.
  - Выдача: `node scripts/grant-admin.mjs <email>` (снять — `--revoke`).
    Через интерфейс роль не меняется. Аккаунт должен уже существовать: иначе
    скриптом можно было бы «занять» чужой адрес пустой записью.
- **`Song.verified` + `verifiedAt`** — подтверждение модератора: аккорды верны и
  песня под них действительно поётся. Автору разбора недоступно.
- Кнопка подтверждения видна только админу; жёлтая галочка с подсказкой
  «Правильный подбор по мнению модератора» — всем, и в каталоге, и на странице
  разбора ([VerifiedBadge](components/VerifiedBadge.tsx)).
- Экшен, как и лайк, **ничего не ревалидирует** — иначе роутер перерисовал бы
  страницу и сбросил транспонирование с прокруткой.

## Закрепление панели аккордов

Кнопка-скрепка в правом верхнем углу панели. В закреплённом виде панель
рендерится **внутрь того же липкого блока, что и тулбар**, а не позиционируется
отдельно: так она всегда встаёт ровно под ним и не требует подбора смещения
(на узком экране тулбар переносится и меняет высоту, любое фиксированное
значение разъехалось бы). Аккорды при этом идут одной строкой с горизонтальной
прокруткой и уменьшенными диаграммами — перенос на вторую строку съел бы
пол-экрана телефона. Состояние запоминается между песнями.

**Настройки читалки сохраняются в обработчиках, а не эффектами на изменение
состояния.** Эффект вида «состояние поменялось → записать» срабатывает и на
первом рендере, когда восстановленное из хранилища значение ещё не применилось,
и успевает затереть его значением по умолчанию. Настройки меняются только
действием пользователя, поэтому запись живёт рядом с этим действием
(`changeTranspose`, `changeFontSize`, … в [SongViewer](components/SongViewer.tsx)).

## Ещё не реализовано

- **Сетлисты** (программа концерта, свайп между песнями). Модели `Setlist` /
  `SetlistItem` (упорядоченная m2m) уже в схеме.
- **Капо в интерфейсе.** Логика (`capoShapeShift`, `transposeKey`) написана и
  покрыта тестами, поле `Song.capo` есть в схеме — но редактор его не сохраняет,
  а читалка не показывает. Фича собрана и не подключена.

## Исправленные дефекты

- **Табулатурные секции рендерились как текст.** `{start_of_tab}` парсился в
  секцию `kind: 'tab'`, но [ChordSheet](components/ChordSheet.tsx) отдавал её в
  колоночную раскладку пропорциональным шрифтом — ASCII-табы (`e|--3--5--|`)
  разъезжались. Теперь такие секции идут моноширинным `<pre>` (`.cs-tab`, свой
  горизонтальный скролл — переносить табы нельзя), а сборка строки вынесена в
  чистую `lineToPlainText` в [columns.ts](lib/chordpro/columns.ts) с тестом на
  побайтовое совпадение. Внутри таб-секции `%` — обычный символ, не разметка.
- **Контраст `--color-faint`.** Было `#5f594e` — 2.80:1 к фону, ниже минимума
  даже для крупного текста, а цветом заданы плейсхолдеры и подсказки. Стало
  `#857e6f` — 4.82:1 (AA), при этом заметно тусклее `--color-muted` (6.05:1).
- **Нулевой байт в исходнике.** В `draftSignature` разделителем был записан
  `\0` вместо пробела — файл выглядел бинарным для grep и подобных инструментов.
  Исправлено; добавлен тест, который ловит подмену разделителя (без настоящего
  разделителя «ab|c» и «a|bc» дают одинаковый отпечаток).
- **Кнопка «Новая» выступала за верхний край нижней панели** — из-за
  отрицательного `margin-top` у `.mnav-fab`. Теперь все пункты имеют зону под
  иконку одной высоты (`.mnav-icon`), поэтому кнопка вписана в панель, а подписи
  стоят на одной линии.
- **Лайк сбрасывал состояние читалки.** Тап по сердечку отправлял форму,
  серверный экшен звал `revalidatePath`, роутер перерисовывал маршрут — и
  транспонирование, размер шрифта и позиция прокрутки слетали. Теперь экшены
  ничего не ревалидируют, а возвращают новое состояние; страница показывает его
  через `useOptimistic` ([SongViewer](components/SongViewer.tsx)). Каталог от
  этого не устаревает — он рендерится динамически на каждый запрос.
  - Заодно настройки читалки переживают и перезагрузку
    ([viewerPrefs.ts](lib/viewerPrefs.ts)): транспонирование запоминается
    **для каждой песни отдельно** (это про конкретную вещь — подобрали под
    голос), а размер шрифта, скорость автоскролла и показ аккордов — общие,
    это про то, как человеку удобно читать вообще. Читается после монтирования,
    иначе разошлась бы гидратация.
